| Multibeam sonar (PR #44, WGPU) — build, adapter selection, sensor output | FUNCTIONAL PASS (scoped) | WGPU backend builds and confirms adapter/backend selection on both platforms (Metal hardware adapter on Mac; `llvmpipe` **software** adapter in Docker — not a real GPU, CPU-based rendering). Real `PointCloud2` output (513 beams × 301 rays) confirmed on Mac Metal under the pre-migration Jazzy+Harmonic track (2026-07-07), and on Docker under Lyrical+Jetty (2026-07-11) — this repo's own logs confirm the bidirectional bridge was created (see [`notes/evidence/multibeam_pointcloud2_evidence.md`](evidence/multibeam_pointcloud2_evidence.md)), and confirm at least one message crossing it in the ROS→Gazebo direction — but not, on their own, a message crossing in the Gazebo→ROS direction that would carry the sonar's actual output (corrected 2026-07-23, an earlier pass here cited that log line without specifying direction). The exact "513 × 301" figure, and the Gazebo→ROS direction of message flow, aren't independently backed by a small evidence artifact in the repo, only by contemporaneous session notes — flagged there, not fabricated after the fact. The 2026-07-20 Docker RAM/CPU load test re-ran the same launch under load and confirmed it stayed alive with real CPU/RAM numbers, but did not itself re-check `PointCloud2` topic content — not counted as a third independent confirmation (traceability gap flagged 2026-07-23). **Mac Lyrical+Jetty itself has build + adapter-selection + `/stats`-topic confirmation, but no direct `PointCloud2` topic-echo on record.** **Does not cover simulation-progress stability** — see the next row and [Known issues](#known-issues) |
| Multibeam sonar (PR #44, WGPU) — simulation-progress stability, `dave_multibeam_sonar` world | PARTIAL | Reproduced and characterized 2026-07-23 on both Mac and Docker, multiple fresh launches, both `wgpu`/`cpu` compute backends: the world either crawls at RTF ~0.012-0.015 (~80× slower than real time) or shows a simulation-progress **stall** for 4+ minutes with no `/stats` messages — on Mac this is a high-CPU stall (CPU climbs 100-200%+, livelock-like behavior); on Docker it's a near-idle stall (CPU ~1%, consistent with a possible deadlock). Not yet confirmed at the source level (no thread dump/lock analysis performed) — this is an external, symptom-level characterization, not a root cause. **Update (2026-07-29, Docker, `lyrical-theme-test`):** live `gdb`-attached one specific run over a ~34-minute window (correct PID confirmed via `ps -eo pid,ppid,pcpu,etime,lstart,cmd`, since a second unrelated `gz-sim-main` — the concurrent 4h stability test — was running at the same time). This run never hit a full stall: `/world/oceans_waves/stats` (the world's actual internal name — it differs from the `dave_multibeam_sonar.world` filename) showed `iterations` continuously increasing across two independent 20s-apart sample pairs, at sustained CPU ~31-32%, not the previously-documented near-idle ~1%. `real_time_factor` was consistently very low, ~0.0008-0.0077 (mostly clustering ~0.0018) — markedly lower than the 0.012-0.015 figure above. Two `gdb` snapshots 30s apart also showed the main thread's program counter had moved (from a step-barrier wait to the inter-step `nanosleep`), independently confirming forward progress. **This refines, not contradicts, the finding above: in this run the world made continuous but extremely slow progress (RTF on the order of 1/500 real-time) rather than a hard stall** — still not usable, but a different failure mode than a full deadlock. Not yet checked whether a true stall occurs later in a longer run. **Update (2026-08-03, Mac/Metal): the "stall" is the startup window.** A continuous t=0→360s scan showed `/stats` emitting fewer than two messages per 25s window for ~80s after launch (vs 69-85 per window once healthy), and the sonar sensor not live until ~145-175s; from t=160s RTF is flat over eight consecutive windows (mean 0.2060, min 0.1866, max 0.2219). The Mac world is therefore **slow, not stalled** — a ~4.5x cost against a 0.9996 no-sonar control, which is itself still unexplained. Docker has **not** been re-measured with this method, so the ~0.0018 Docker figure above stands unrevised and may be a different problem. Single run; see [`notes/results/multibeam_startup_2026-08-03/`](results/multibeam_startup_2026-08-03/). See [Known issues](#known-issues) |

| USBL | FUNCTIONAL PASS (combined evidence, workaround) | Two independent, real bugs found and worked around, not one. **Bug 1 (2026-07-22):** not a GUI crash — the Gazebo **server** process aborted (`SIGABRT`) on a libstdc++ `std::normal_distribution` assertion failure, because `usbl_tutorial.world` set `<sigma>0.0</sigma>` on both `UsblTransponder` plugin instances (`UsblTransponder.cc:263`, unvalidated). Worked around at the world-file level (`sigma` → `0.0001`), not a plugin-level fix — baked into `docker/lyrical.arm64v8.dockerfile`. **Bug 2 (2026-07-29, found while trying to close the combined-evidence gap below):** `dave_sensor.launch.py` only appends `gz sim`'s `-r` (run-on-start) flag when given `paused:=false` explicitly; without it the world loads paused, and both `UsblTransponder`/`UsblTransceiver`'s `PostUpdate` gate their `rclcpp::spin_some()` call behind `if (!_info.paused)` — so every ROS2 subscription callback (`interrogation_mode`, `common_interrogation_ping`) structurally never fires, independent of DDS-level topic matching (which reports matched subscribers regardless). Worked around via the launch arg only — `paused:=false`, no world-file/plugin change needed. **Upgraded PARTIAL → FUNCTIONAL PASS (2026-07-29):** re-launched with `paused:=false` and, in one continuous session, confirmed both the no-abort state (sigma fix holding) and real `dave_interfaces/msg/Location` data streaming from both transponders after publishing to `interrogation_mode`/`common_interrogation_ping` — closing the combined-evidence gap flagged 2026-07-23. Neither the plugin-level sigma fix nor an upstream report (which should now cover both bugs) has been filed yet. See [Known issues](#known-issues) and [`notes/usbl-gui-crash-investigation.md`](usbl-gui-crash-investigation.md) |
