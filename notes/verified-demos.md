### `dave_multibeam_sonar` — as recorded 2026-07-23 → 2026-08-03

Reproduced and characterized 2026-07-23 on both Mac and Docker, multiple fresh launches, both `wgpu`/`cpu` compute backends: the world either crawls at RTF ~0.012-0.015 (~80× slower than real time) or shows a simulation-progress **stall** for 4+ minutes with no `/stats` messages — on Mac this is a high-CPU stall (CPU climbs 100-200%+, livelock-like behavior); on Docker it's a near-idle stall (CPU ~1%, consistent with a possible deadlock). Not yet confirmed at the source level (no thread dump/lock analysis performed) — this is an external, symptom-level characterization, not a root cause. **Update (2026-07-29, Docker, `lyrical-theme-test`):** live `gdb`-attached one specific run over a ~34-minute window (correct PID confirmed via `ps -eo pid,ppid,pcpu,etime,lstart,cmd`, since a second unrelated `gz-sim-main` — the concurrent 4h stability test — was running at the same time). This run never hit a full stall: `/world/oceans_waves/stats` (the world's actual internal name — it differs from the `dave_multibeam_sonar.world` filename) showed `iterations` continuously increasing across two independent 20s-apart sample pairs, at sustained CPU ~31-32%, not the previously-documented near-idle ~1%. `real_time_factor` was consistently very low, ~0.0008-0.0077 (mostly clustering ~0.0018) — markedly lower than the 0.012-0.015 figure above. Two `gdb` snapshots 30s apart also showed the main thread's program counter had moved (from a step-barrier wait to the inter-step `nanosleep`), independently confirming forward progress. **This refines, not contradicts, the finding above: in this run the world made continuous but extremely slow progress (RTF on the order of 1/500 real-time) rather than a hard stall** — still not usable, but a different failure mode than a full deadlock. Not yet checked whether a true stall occurs later in a longer run. **Update (2026-08-03, Mac/Metal): the "stall" is the startup window.** A continuous t=0→360s scan showed `/stats` emitting fewer than two messages per 25s window for ~80s after launch (vs 69-85 per window once healthy), and the sonar sensor not live until ~145-175s; from t=160s RTF is flat over eight consecutive windows (mean 0.2060, min 0.1866, max 0.2219). The Mac world is therefore **slow, not stalled** — a ~4.5x cost against a 0.9996 no-sonar control, which is itself still unexplained. Docker has **not** been re-measured with this method, so the ~0.0018 Docker figure above stands unrevised and may be a different problem. Single run; see [`notes/results/multibeam_startup_2026-08-03/`](results/multibeam_startup_2026-08-03/). See [Known issues](known-issues.md)

### `dave_ocean_waves_sonar_integrated` — as recorded 2026-07-23 → 2026-07-29

Same `sonar-demo`-branch resolution as above (2026-07-22) — only uses `multibeam_sonar_system`, smoke-tested successfully. Re-checked 2026-07-23 with a clean, uncontaminated single-process sample: the world runs (not stalled like `dave_multibeam_sonar` — `sim_time` clearly progressing) but at a confirmed slowdown, roughly RTF 0.03 by endpoint delta over a noisy 20s spot sample (sim_time advanced 0.55s while the sampling command ran for 20s) — treat this as an order-of-magnitude estimate, not a precise figure. **Update (2026-07-29):** a fresh clean single-process re-check (correct PID confirmed via `ps`) over ~4.5 minutes and 4 sample points found `iterations` continuously increasing throughout, at a delta-based RTF consistently in the **~0.1-0.4** range — roughly 10× better than the 2026-07-23 figure. Measured with two other `gz-sim-main` instances competing for CPU on the same container (a 4h stability test + a `dave_multibeam_sonar` repro), an atypical, non-isolated condition that if anything should have hurt this result, not helped it. Status held at `PARTIAL` pending a clean isolated re-benchmark and an explanation for the climbing CPU, but the old RTF ~0.03 figure is superseded — this world looks meaningfully more usable than previously documented, and notably better than `dave_multibeam_sonar` despite sharing the same `multibeam_sonar_system` plugin.
