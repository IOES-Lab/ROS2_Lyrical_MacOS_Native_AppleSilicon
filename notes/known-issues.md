## Known issues, resolved findings and withdrawn claims

- **The integrated Glider `enable_deadband` bridge was asymmetric in one direct Docker test** (2026-08-27) — on `/model/glider_slocum/joint/propeller_joint/enable_deadband`, Gazebo `true` reached ROS, but ROS `true` was not observed by a simultaneous Gazebo echo and timed out with exit 124. The ROS publisher returned success, the launch log created both bridge directions, and ROS reported both bridge endpoints. A control using the same `std_msgs/msg/Bool` ↔ `gz.msgs.Boolean` converter on an isolated topic passed both directions, so the generic Bool conversion is not the demonstrated blocker. This is one integrated run and the exact cause remains open. The neighbouring `cmd_thrust` control did cross ROS→Gazebo and changed `ang_vel`, so the finding is specific to the deadband path rather than all Glider actuator commands. [`results/glider_direct_validation_2026-08-27/`](results/glider_direct_validation_2026-08-27/)

- **DVL sensor worlds crash on the tested Mac in Gazebo Sensors before producing DVL data** (2026-08-26) — the exact DAVE Wiki GUI command, the same DAVE world headless, the official `ros_gz_sim_demos` DVL launch, and the official stock DVL world changed from `ogre2` to `ogre` all terminate in `gz::sim::systems::SensorsPrivate::RenderThread()` / `WaitForInit()` with SIGSEGV. Docker runs the same DAVE Quickstart and controlled DVL worlds successfully, so this is not a DAVE-only, GUI-only or `ogre2`-only observation. The exact lower-level macOS cause is not established. [`results/dvl_direct_validation_2026-08-26/`](results/dvl_direct_validation_2026-08-26/)
- **DAVE's custom `DVLBridge` drops the source frame ID** (2026-08-26) — Gazebo DVL messages carry a populated frame ID, but every directly captured ROS DAVE message has `header.frame_id: ''`. Source inspection confirms that `DVLBridge.cc` copies the timestamp but never assigns the frame. The official `ros_gz` DVL conversion, tested separately with a C++ subscriber, preserves `tethys/base_link/teledyne_pathfinder_dvl`; therefore this is scoped to DAVE's custom bridge, not the message type or Gazebo sensor. [`results/dvl_direct_validation_2026-08-26/source_audit.txt`](results/dvl_direct_validation_2026-08-26/source_audit.txt)
- **Shipped DAVE DVL water-mass configuration does not name environmental variables** (2026-08-26) — Gazebo's DVL API interprets `<water_velocity><x/y/z>` as environmental-variable names, but all eight standalone DAVE DVL models and REXROV use the literal text `0.` and DAVE contains no matching environment preload. The exact shipped water-mass run produced 20/20 `DVL_TARGET_UNSPECIFIED` samples with no beam locks. A corrected control using named variables plus dynamic environmental data produced 20/20 `DVL_TARGET_WATER_MASS` samples, four locks, the expected mean-layer range and the expected water speed. The sensor capability works; the distributed configuration does not exercise it. [`results/dvl_direct_validation_2026-08-26/09_water_mass_docker/`](results/dvl_direct_validation_2026-08-26/09_water_mass_docker/) · [`10_water_mass_corrected_control/`](results/dvl_direct_validation_2026-08-26/10_water_mass_corrected_control/)

- **SeaPressure publishes kPa-sized numbers in the Pascal-defined ROS field** (2026-08-26) — ten controlled conditions were run on both Mac and Docker. At the controlled surface the plugin published `101.325`; at `|z|=10 m` it published `199.3888`. `sensor_msgs/msg/FluidPressure` defines `fluid_pressure` in Pascals, so contract-following consumers expect `101325` and `199388.8`. The same values appeared on both platforms and the baseline Gazebo Transport message also carried `pressure: 101.325`; no claim is made here about the Gazebo message's unit contract. [`results/seapressure_full_validation_2026-08-26/`](results/seapressure_full_validation_2026-08-26/)
- **SeaPressure silently ignores three documented SDF elements** (2026-08-26) — `<saturation>50</saturation>` at `z=-10 m` still produced `199.3888`, `<noise_sigma>0.123</noise_sigma>` still produced variance `9.0` rather than `0.015129`, and `<update_rate>2</update_rate>` still produced a median timestamp interval of about `0.001 s` rather than `0.5 s`. These discriminating controls passed identically on Mac and Docker. Source inspection explains the result: `saturation` is parsed then never used, while `noise_sigma` and `update_rate` are not parsed. [`results/seapressure_full_validation_2026-08-26/`](results/seapressure_full_validation_2026-08-26/)
- **SeaPressure uses `abs(z)`, so a probe above the configured surface origin reads as submerged** (2026-08-26) — in a controlled world where `z=0` represented the surface, probes at `z=-10 m` and `z=+10 m` both published pressure `199.3888` and inferred depth `10.0`. This is runtime-confirmed on Mac and Docker and follows `depth = std::abs(Z)` in the plugin. Whether a different world convention makes that intentional is not established; the demonstrated failure is for a surface-at-zero convention. [`results/seapressure_full_validation_2026-08-26/`](results/seapressure_full_validation_2026-08-26/)
- **SeaPressure ROS messages have an empty `header.frame_id`, while variance remains non-zero without sampled noise** (2026-08-26) — every retained pressure frame on both platforms had `frame_id: ''`; source assigns pressure and variance but never the header frame. Five post-warmup frames per condition were identical, consistent with the source's commented-out Gaussian-noise line and `+= 0.0`. The runtime data establishes deterministic output in these short runs, not a long-duration statistical guarantee, and it cannot determine what maintainers intend `variance: 9.0` to mean. [`results/seapressure_full_validation_2026-08-26/`](results/seapressure_full_validation_2026-08-26/)

- **`UnderwaterCamera`'s `attenuationR`/`backgroundR` act on Blue and `attenuationB`/`backgroundB` act on Red** (2026-08-26) — the input frame is converted to OpenCV BGR (`cv::COLOR_RGB2BGR`, `UnderwaterCamera.cc:328`), while `Configure()` stores the SDF values in tag order R→`[0]`, G→`[1]`, B→`[2]` (lines 227–276). The transform loop then applies `attenuation[c]` and `background[c]` to `cv::Vec3b[c]` (lines 426–433), where index `0` is Blue and index `2` is Red. **Runtime-confirmed and discriminating:** in one controlled scene at 3.975 m with input BGR `[55, 78, 109]`, the Wiki's murky values (`attenuationR/G/B` = 0.8/0.5/0.2, `backgroundR/G/B` = 85/107/47) predict `[83, 103, 74]` under the current direct indexing and `[50, 103, 85]` under a semantically correct RGB mapping. Observed output was `[83, 103, 74]` on both Mac and Docker. The green channel predicts `103` either way and does not discriminate; blue and red do. A user setting a red attenuation therefore attenuates blue. **Not affected:** the default configuration, where all three attenuations are `1/30` and all backgrounds `0`, so the mapping is unobservable — `[48, 68, 95]` was predicted and measured. `UnderwaterCamera.cc` itself is unmodified in this checkout at `6aef91c` (last upstream change `9f159f4`, 2025-07-02), though the checkout as a whole is not pristine. Not yet reported upstream. [`results/underwater_camera_direct_validation_2026-08-26/`](results/underwater_camera_direct_validation_2026-08-26/)

- **`blueview_p900` ships `<update_rate>30</update_rate>`, which the sensor cannot meet and the hardware does not do** (2026-08-06) — the sonar actually achieves ~2.8 frames/s, so a 30 Hz request functions as "as fast as possible" rather than as a limit; a real BlueView P900 tops out near 15 Hz. Lowering it is the only intervention found so far that improves RTF with no code change and no rebuild: **10 Hz → RTF 0.598 (+14%, n=3), 2 Hz → 0.814 (+55%, n=2)** against 0.5243 at the shipped 30 Hz (n=3), removing 26% and 75% of the sonar's overhead over the no-sonar control. Monotonic, and both clear the 8% repeat band. Context: making the sonar *faster* backfires — skipping the visualisation image let the compute thread run 2.4x more frames (GPU #550 → #1300) and cost 40% RTF, because the thread consumes whatever capacity it can get. Frequency is the knob, not speed. n is 3/3/1/2 across 30/10/5/2 Hz; output fidelity at lower rates was not assessed. See [`notes/results/updaterate_2026-08-06/`](results/updaterate_2026-08-06/).
- **The documented DAVE build produces an unoptimised plugin** (2026-08-05) — neither `gazebo/DEMO_GUIDE.md` nor `gazebo/DEMO_GUIDE_AppleSilicon_MacOSX.md` passes `--cmake-args -DCMAKE_BUILD_TYPE=Release`, no package `CMakeLists.txt` sets a default, and colcon supplies none — so all 14 DAVE packages compile with no `-O` flag. - **`SphericalCoords.cc`'s Lyrical/Jetty migration patch can silently mask a real conversion failure as zero/origin, in *both* conversion directions** (found during 2026-07-23 documentation audit, not yet fixed) — the new `gz::math::CoordinateVector3`-based API returns `std::optional`s, and the patch substitutes a default value without returning failure whenever those are empty, in both directions:
  - [`TransformFromSphericalCoord`](../patches/dave_lyrical_jetty_migration_mac.diff): only assigns `cartVec` from the result `if (cartOpt && cartOpt->AsMetricVector())`; `cartVec` stays at its default-constructed value (0,0,0) if that check fails, and the service still returns success.
  - `TransformToSphericalCoord` (same patch, confirmed 2026-07-23 while re-checking the first bullet — not previously documented): `response->latitude_deg`/`longitude_deg`/`altitude` are each computed as `(scOpt && scOpt->Lat()/Lon()/Z()) ? ... : 0.0`, so any of the three can silently become `0.0` independently while the service still returns success.

  In both cases, a real request that happens to legitimately resolve near zero/the origin becomes indistinguishable from a silently-failed conversion. Not yet observed to actually misfire in practice, but worth fixing before relying on either service: log an error and/or return a failure response when the conversion fails, rather than substituting a default value silently. **Runtime update 2026-08-26:** three finite round trips per platform did not trigger this optional-empty branch, and NaN propagated as NaN rather than falling back to zero. That test confirms the separate input-validation issue above, not this source-only fallback path.
